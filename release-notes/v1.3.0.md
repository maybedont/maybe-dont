# Release Notes

v1.3.0 adds a purpose-built REST endpoint for validating agent actions before execution, enabling integration with external agent frameworks like OpenHands.

---

## New

### Action Validation Endpoint

A new `POST /api/v1/action/validate` endpoint lets external agent frameworks validate actions through the gateway's policy engines before executing them. The endpoint accepts an action target and parameters, runs them through both CEL and AI policy evaluation, and returns an allow/deny decision with a risk level.

```bash
curl -X POST http://localhost:8080/api/v1/action/validate \
  -H "Content-Type: application/json" \
  -d '{
    "target": "execute_bash",
    "parameters": {"command": "rm -rf /"},
    "external_id": "action-123",
    "context": {
      "thought": "Clean up temporary files"
    }
  }'
```

```json
{
  "request_id": "a1b2c3...",
  "allowed": false,
  "risk_level": "high",
  "message": "Action denied by policy: destructive command detected"
}
```

Key details:

- Actions are evaluated as tool calls through the existing CEL and AI request policy engines
- Risk level maps to `high`, `medium`, `low`, or `unknown` — compatible with OpenHands' `SecurityRisk` enum
- `external_id` field enables correlating gateway audit entries back to the caller's records
- Audit entries include `source: "action"` to distinguish from MCP and CLI validation paths
- Respects the `include_argument_values` audit config for parameter logging

### Audit Log Source Field

Audit log entries now include a `source` field (`"mcp"`, `"cli"`, or `"action"`) to distinguish which validation path produced the entry.

---

## Changed

### Gateway Starts Without Downstream MCP Servers

The gateway no longer requires at least one downstream MCP server to start. This supports deployments that use only CLI validation, action validation, or native tools without proxying to any downstream servers.

### Policy Test Match Rate Semantics

The `maybe-dont test policies --matrix` output now uses clearer metric naming:

- **Match Rate** (used for pass/fail threshold) — counts both exact matches and extra-policy-only cases
- **Strict Match Rate** — only counts exact matches, penalizing extra policy triggers

The threshold now uses the lenient metric, so tests that make the correct decision but trigger additional policies no longer fail the suite.
