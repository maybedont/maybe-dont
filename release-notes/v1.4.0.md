# Release Notes

v1.4.0 adds the intercept endpoint for validating agent tool calls via REST hooks, a new AI response rule for detecting agent-restricted content, and fixes for session tracking on cloud deployments.

---

## Breaking Changes

### `list_sessions` field renames

The `maybedont__list_sessions` native tool now uses connection-based terminology instead of activity-based:

| Before | After |
|--------|-------|
| `include_inactive` | `include_disconnected` |
| `active_session_count` | `connected_count` |
| `inactive_session_count` | `disconnected_count` |

Sessions are now classified by whether they have an active SSE connection, not by whether they have downstream clients. This is more accurate for cloud deployments where sessions can be connected but not yet have downstream clients initialized.

## New

### Intercept Endpoint

A new `POST /api/v1/intercept` endpoint validates tool calls and CLI commands from agent hook scripts. This enables integration with agent frameworks that use pre/post-execution hooks (e.g., Claude Code hooks, Gemini CLI hooks) to enforce policies before or after tool execution.

```bash
curl -X POST http://localhost:8080/api/v1/intercept \
  -H "Content-Type: application/json" \
  -d '{
    "event": "tools/call",
    "phase": "request",
    "payload": {
      "name": "Bash",
      "arguments": {"command": "rm -rf /"}
    }
  }'
```

```json
{
  "interceptor": "maybe-dont",
  "type": "validation",
  "phase": "request",
  "valid": false,
  "severity": "error",
  "messages": [{"message": "Destructive command detected", "severity": "error"}],
  "durationMs": 42,
  "info": {"request_id": "...", "server_version": "1.4.0", "results": [...]}
}
```

Key details:

- **Request and response phases**: `"phase": "request"` validates before execution; `"phase": "response"` validates after (requires `payload.result` with the tool output)
- **Shell tool dual evaluation**: Tools listed in `intercept.shell_tool_names` (default: `["Bash"]`) are parsed as CLI commands and evaluated against both `cli_expression` and `mcp_expression` CEL rules, with results merged
- **Optional context**: Pass `context.sessionId`, `context.traceId`, and `context.principal` for audit correlation
- Enabled by default — disable with `intercept.enabled: false` or `MAYBE_DONT_INTERCEPT_ENABLED=false`
- Audit entries use `source: "intercept"` to distinguish from MCP, CLI, and action validation paths

### AI Response Rule: `detect-agent-restricted-content`

A new built-in AI response rule (disabled by default) that checks whether response content contains explicit signals restricting AI agent access — such as "AI agents should not access", machine-readable `ai-access: restricted` markers, or agent-specific access warnings.

Enable it in your `ai_response_rules.yaml` or by setting `enabled: true` on the rule.

## Fixed

### Session context enrichment on Streamable HTTP

Fixed missing client IP and User-Agent on sessions when using the Streamable HTTP transport. Context enrichment now runs in HTTP middleware rather than SDK callbacks, ensuring metadata is available for all request types including session registration.
